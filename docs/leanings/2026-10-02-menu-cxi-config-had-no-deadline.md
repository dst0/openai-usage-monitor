# 2026-10-02 — Menu `cxi config` writes had no deadline

- **Status:** Resolved
- **Task/context:** Follow-up to the Auto-Switch Settings submenu (#51). Its rows stay disabled until each `cxi config` write reports, and the Swift client ran the CLI with `Process.waitUntilExit()` and no timeout. #51 listed a timeout as a rejected approach because a proper one needs process-group termination and a test proving no descendants survive.
- **Unexpected observation or failure:** A `cxi config` run that never exits leaves `pendingAutoSwitchSettingWrites` above zero, so every submenu row stays disabled until the Monitor is restarted, and every later write queues behind it on the serial config queue.
- **Evidence:** `Sources/CodexClient.swift` `runConfig` before this change; the Rust `config` command takes the switcher lock with a blocking `flock`, so a stuck holder blocks it indefinitely.
- **Approaches tried:**
  - **Attempt:** `Process` with `terminate()` after a deadline.
    - **Outcome:** Did not work
    - **Why:** It signals only the direct child, and `Process` cannot put the child in its own process group, so anything it started survives holding its descriptors.
  - **Attempt:** Reap with `waitpid(WNOHANG)`, then `killpg` the group on every path.
    - **Outcome:** Did not work
    - **Why:** Once the leader is reaped and the group is empty, its ID can name an unrelated process group. The group must be killed while the leader is still an unreaped zombie, so exit is detected with `waitid(... WNOWAIT)`.
  - **Attempt:** Hand an unreaped killed run to a background reaper and let the queue move on.
    - **Outcome:** Partial
    - **Why:** It unfreezes the menu, but a run stuck in the kernel could still finish its rename after a newer write. The runner now refuses to start the next command until the reaper has it, waiting at most the reap grace, so writes stay ordered and the menu still gets its rows back.
  - **Attempt:** `posix_spawn` with `POSIX_SPAWN_SETPGROUP`, `POSIX_SPAWN_CLOEXEC_DEFAULT`, default signals, and `/dev/null` on the standard descriptors (`Sources/BoundedCommand.swift`).
    - **Outcome:** Worked
    - **Why:** The command and everything it starts share one group that can be killed as a unit, and nothing inherits a Monitor descriptor.
- **Root cause:** An unbounded wait on an external process gated the menu's enabled state.
- **Resolution:** `runConfig` runs through `BoundedCommand` with a 15-second deadline. A stopped run reports failure; the submenu already judges a write by reading the registry back, and the weekly reset client now does the same, because a run killed after its registry rename (during the status cache sync) did save.
- **Verification:** `tests/BoundedCommandTests.swift` proves exit status, signal, missing executable, and that a descendant holding a FIFO lets it go both after a normal exit and at the deadline (EOF on the FIFO, no process-list read). `tests/AutoSwitchSettingsMenuTests.swift` proves a hung write gives the rows back with a warning and the saved mark, the next write saves, and a stopped weekly reset write that saved reports success. The macOS Swift CI job runs both.
- **Prevention/follow-up:** A killed run that was between creating and renaming its `accounts.<pid>.<nonce>.tmp.json` staging file leaves that `0600` file behind; the Rust core does not yet remove stale staging files whose writer is gone. A descendant that calls `setsid` escapes the group kill.
- **Reusable learning:** Bound every CLI run the menu waits on, start it in its own process group, kill the group before reaping the leader, and keep a serial writer queue closed until a killed writer is reaped.
- **References:** `Sources/BoundedCommand.swift`, `Sources/CodexClient.swift` (`runConfig`, `setAutoResetWeekly`), `AGENTS.md` timeout table and Auto-Switch Settings Truth Invariant, PR #51.
