# 2026-09-20 — historical log redaction needs a quiesced bounded migration

- **Status:** Resolved
- **Task/context:** Extend the persistent-output redaction boundary to Monitor-owned logs created before an upgrade, while removing the repository's existing Rust file-structure debt.
- **Unexpected observation or failure:** Redacting only new writes left older active, archived, and restart-worker logs unchanged. The first migration also stopped writers before later fallible build steps, read an entire line before applying its size limit, skipped restart-worker logs, could leave rewrite temporary files after some errors, and force-removed a recovery worker that is contractually allowed to finish. The first app replacement used `rm -rf` followed by `cp -R`, so a copy failure could leave no installed app. A writer/rotation process could also retain the old inode and write legacy data after migration unless both paths shared a lifecycle lock. Later review found four narrower races: an unlink while holding a lock could let a writer create a second inode, a writer already waiting on the old inode could proceed after unlink, `readdir` I/O errors looked like EOF, backup cleanup still ran with rollback armed, and a reused Monitor PID could be signalled after daemon retirement.
- **Evidence:** Focused regressions reproduced spaced JSON values that crossed whitespace-token boundaries, an unsafe suffix after an existing marker, a line larger than the migration bound, invalid UTF-8, malformed Brotli, a symlinked restart log, exact and malformed Monitor filenames, repeated directory enumeration, injected `readdir` errors, lifecycle-lock contention/unlink/pre-opened waiter, and all exact Monitor archive prefixes. An uninstall regression revealed that duplicated directory descriptors shared an offset, while bundle-swap tests reproduced copy, initial backup-rename, rollback, interrupt-boundary, rollback-failure preservation, and committed-swap cleanup boundaries. A process-guard regression changes a captured PID start time and proves it is not signalled.
- **Approaches tried:**
  - **Attempt:** Apply redaction only at every new persistent-output sink.
    - **Outcome:** Partial.
    - **Why:** It protected future output but could not change data already present before installation.
  - **Attempt:** Rewrite historical files after a best-effort process stop and reject oversized lines after `read_until` returned.
    - **Outcome:** Did not work.
    - **Why:** A stale writer could retain the retired inode, later build failure left the installed Monitor unavailable, and a newline-free input could allocate beyond the intended bound before rejection.
  - **Attempt:** Stage and strictly verify the app first, stop its producers while allowing an in-flight recovery worker to finish, stream through explicit line/directory bounds, atomically replace only changed exact-owned logs, and activate the app through a rollback-capable rename.
    - **Outcome:** Worked.
    - **Why:** The migration now has a fail-closed ownership boundary, bounded memory per line, source preservation on invalid input, exact `0600` replacement modes, true inode idempotence, and cleanup for every temporary-file error path.
- **Root cause:** Runtime redaction and upgrade migration are different lifecycle boundaries. Safe migration additionally requires producer quiescence without interrupting recovery, a shared writer/migration lock whose inode cannot be recreated by a stale writer or used after being unlinked, exact file ownership grammar, bounded decoding and error-aware enumeration, atomic replacement, rollback, PID identity revalidation, and crash/error cleanup.
- **Resolution:** The installer now stages and strictly verifies the app before stopping the verified Monitor and daemon, revalidates a candidate Monitor PID by executable and start time immediately before signalling it, waits for an in-flight restart worker to finish, migrates logs, and activates the staged bundle with a preserved rollback copy. The lock is created only by installation, while append/rotation takes it shared and migration takes it exclusively; daemon startup validates the existing lock but cannot initialize it. After flock acquisition, a waiter reopens the pathname and requires the same device/inode, so an unlinked pre-opened file cannot authorize a later write. Directory reads clear and check `errno`; a `readdir` error cannot skip a legacy file. A bundle commit disarms rollback before backup cleanup. The Rust migration covers the three active logs, exact numeric timestamp Brotli Q6 archives, and exact two-field numeric restart-worker logs; it preserves foreign and official Codex Desktop files. Structured redaction handles whitespace-separated JSON values and rejects marker-prefix suffix bypasses. The Rust file-limit and one-struct-per-file gate is green after the legacy module splits.
- **Verification:** `cargo test --all-targets` passed the Rust unit and integration suites; the file-limit and one-struct-per-file gate passed; production `cargo clippy --bin codex-mon -- -D warnings` passed; install/uninstall, restart-worker wait, bundle-swap failure, PID-reuse guard, and installer-order shell tests passed; the complete Swift suite passed. Focused migration tests cover all owned scopes, foreign preservation, exact filename grammar, `0600`, inode idempotence, lifecycle lock contention/unlink/pre-opened waiter and daemon non-recreation, repeated, excessive, and injected-error directory enumeration, oversized and invalid UTF-8 input, malformed Brotli, symlinks, source preservation, and temporary cleanup.
- **Prevention/follow-up:** Keep archive and recovery filename ownership grammar centralized. Reopen directory descriptors independently, bound each enumeration, and clear/check `errno` for every `readdir` null. Create lifecycle coordination in installation only; daemon validation must never create it, and every waiter must revalidate the named inode after flock acquisition. Revalidate a PID's executable and start identity after every operation that may wait before signalling. Add any new persistent Monitor sink to both runtime redaction and the quiesced upgrade migration contract; never force-remove an in-flight recovery worker during installation.
- **Reusable learning:** A redaction fix is incomplete until upgrades handle old exact-owned data under verified writer quiescence with bounded, atomic, fail-closed rewriting and stable process/lock identities.
