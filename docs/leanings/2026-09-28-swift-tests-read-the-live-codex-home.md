# 2026-09-28 — Swift tests read the live Codex home and every AppDelegate created it

- **Status:** Resolved
- **Task/context:** Follow-up to the remaining shared state listed in [2026-09-28 — Concurrent Swift suite runs isolated by an injected defaults store](2026-09-28-concurrent-swift-suites-isolated-by-injected-defaults.md). `./scripts/test_swift.sh` is run by developers and by several agents on one host, so it must not read or change the developer's `~/.codex`, which ChatGPT.app and the Rust core own.
- **Unexpected observation or failure:** The AppDelegate suite built menus with `CodexClient.shared`, which read the live `accounts.json` settings, and Test 5 read the live registry to assert only that a `Bool` was a `Bool`. Tests that did isolate themselves did it by `setenv("CODEX_HOME", ...)`, a process-wide change that every later check inherits unless each exit path restores it. Every `AppDelegate`, including the ones tests build, created `$HOME/.codex` if it was missing: `SingleInstanceGuard`'s default lock path ran `createDirectory` from the delegate's stored-property initializer and read `HOME`, not `CODEX_HOME`. `HelpsDocHelper` also fell back to `~/.codex/helps.html`.
- **Evidence:**
  - Before the change, `./scripts/test_swift.sh` under `sandbox-exec` with `(deny file-read* file-write* (subpath "$HOME/.codex") (with send-signal SIGKILL))` was killed (`Killed: 9`, exit 137) in `app_delegate_test`. The two defaults suites it left behind (`app-delegate` and `fresh`) show where: the first `makeTestAppDelegate` in Test 4, that is, the delegate initializer's lock path, before any test read a file.
  - The new `tests/swift_test_codex_home_isolation.sh`, run against the pre-change tree (`git archive 4eb6c4f`), reports every `CodexClient.shared`, `CodexClient()`, and `CODEX_HOME` `setenv`/`getenv` in the tests, three `.codex` path literals in `Sources/` (`CodexClient.swift`, `QuotaModels.swift`, `SingleInstanceGuard.swift`), and the `HOME` read.
  - After the change, the whole `./scripts/test_swift.sh` passes under that sandbox profile. Both Codex-home test binaries also pass with `CODEX_HOME` set to a second denied directory; `sandbox-exec` with the same profile kills `/bin/ls` on either path, so the profile is live.
- **Approaches tried:**
  - **Attempt:** Keep the static `CodexClient.codexHome` and have each test set `CODEX_HOME` first.
    - **Outcome:** Rejected.
    - **Why:** It is process-wide state that one forgotten test undoes, a static check cannot tell which home a later call reads, and the lock path ignored `CODEX_HOME` anyway.
  - **Attempt:** Run the Swift test binaries under `sandbox-exec` from `test_swift.sh` as the guard.
    - **Outcome:** Rejected as the enforced check; kept as the audit.
    - **Why:** `sandbox-exec` is deprecated, and a developer or agent already running inside a restrictive sandbox may not be allowed to apply another profile. A check that silently skips there would be a weakened gate. The static check runs everywhere, and the sandbox run is the evidence that the rules are enough.
  - **Attempt:** Give `CodexClient` an injected `codexHome`, resolve the live one only in `CodexClient()`, derive every Monitor path (including the lock and the help-page copy) from the client that `AppDelegate` was given, and give tests a `TestCodexHome`.
    - **Outcome:** Worked.
    - **Why:** The code under test reads exactly the fixture home, so tests can assert that a value came from it, and a missing fixture home proves that building a delegate, its menu, and its watchers creates nothing.
- **Root cause:** Confirmed. The Codex home was a process-wide static (`CodexClient.codexHome`, read from the environment on every access) rather than a dependency of the client, and the single-instance lock resolved and created its directory while the delegate was being constructed instead of when launch takes the lock.
- **Resolution:** `CodexClient` stores `codexHome`; `CodexClient()` (as `CodexClient.shared`) passes `CodexClient.liveCodexHome`, and `init(codexHome:distributionRunner:desktopAppAccountIdProvider:)` serves tests. The status cache, auth, registry, session marker, config, restart-cancellation marker, window-bounds files, and help-page copy are all read from the client's home. `SingleInstanceGuard(codexHome:)` only names `monitor.lock`; `tryAcquire()` at launch still creates a missing home, because the installer creates `~/.codex` first and without it a missing home would look like another running Monitor. The lock now follows `CODEX_HOME` like the rest of the app and `scripts/uninstall.sh`. `tests/TestCodexHome.swift` provides per-run homes, and `tests/AppDelegateCodexHomeTests.swift` (Test 5) checks each path. `tests/swift_test_codex_home_isolation.sh` runs from `test_swift.sh` and in its own required CI step.
- **Verification:** `./scripts/test_swift.sh` with a fresh `CLANG_MODULE_CACHE_PATH`, plain and under the sandbox profile; the guard's own fixture checks (each rule rejects a sample violation and an unreadable file fails); `cargo test --locked --test ci_workflow_policy` (it failed until the new script had a CI step); the production sources compiled with the installer's flags.
- **Prevention/follow-up:** The static check and Test 5 guard the fix. The Swift tests still stat `~/.local/bin/codex-mon` and `~/dev/openai-usage-monitor/...` when they build a distribution process (`CodexClient.cliExecutableURL`), and `loadCachedSnapshot()` still asks `NSRunningApplication` whether ChatGPT is running. Neither touches the Codex home, and neither is injected yet.
- **Reusable learning:** Make a data directory a constructor dependency of the client that reads it, resolve the live one in exactly one composition root, and never create it while constructing an object; create it only in the step that needs it.
