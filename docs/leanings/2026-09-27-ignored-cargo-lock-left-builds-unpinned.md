# 2026-09-27 — Ignored Cargo.lock left every build unpinned

- **Status:** Partial
- **Task/context:** Commit `codex-switcher/Cargo.lock` for the `codex-mon`/`cxi` binary and make CI, the installer, and the shell tests build it with `--locked`, following up the prevention note in [2026-09-26-ci-cargo-cache-key-hashed-ignored-lockfile.md](2026-09-26-ci-cargo-cache-key-hashed-ignored-lockfile.md).
- **Unexpected observation or failure:** The blanket `*.lock` rule in `.gitignore` (present since the initial release) kept the lockfile out of the repository, so no two builds were guaranteed to use the same crates. CI ran `cargo generate-lockfile` and then `cargo test` without `--locked`, and `scripts/install.sh` ran `cargo build --release`: each resolved the newest semver-compatible releases at that moment. The earlier cache fix made the key follow the resolution, but the resolution itself still floated and nothing reviewed it.
- **Evidence:** CI run `36259953560` on main `93b9c1a` logged `Locking 141 packages to latest compatible versions` and saved cache key `macOS-cargo-49a04bed…-74f3856d…`. The owner's main checkout held an ignored, older local resolution whose `hashFiles` digest (`2db1c131…`) differed from CI's, so local and CI builds had already diverged. Resolving in this worktree with rustc/cargo 1.98.1 (`cargo metadata`) produced a lockfile whose `hashFiles` digest, computed as SHA-256 over the file's raw SHA-256 (the same method reproduces the toolchain half `49a04bed…`), is `74f3856d…`: byte-identical to what CI tested, so committing it bumped nothing. With cargo 1.98.1 on a scratch crate: `--locked` with no lockfile fails with `cannot create the lock file … because --locked was passed`; with a stale one, `cannot update the lock file`; `--frozen` fails the same way; `cargo test -- --locked` still creates the lockfile because the flag goes to the test binary; `cargo fmt --check` never creates one and `cargo fmt --locked` is rejected. In a scratch clone with an ignored local `Cargo.lock`, `git pull` of a commit that stops ignoring and adds the file replaced it without a conflict. Before the fix, the new policy tests failed on the live tree with exactly: `ci.yml` lines 49 (`cargo generate-lockfile`) and 64 (`cargo test --verbose`); `scripts/install.sh` line 353 and `tests/log_permissions_and_uninstall.sh` line 47; `Cargo.lock` not committed and matched by `.gitignore`; and `hashFiles('codex-switcher/Cargo.lock')` naming an uncommitted file.
- **Approaches tried:**
  - **Attempt:** Keep `*.lock` and add `!Cargo.lock`.
    - **Outcome:** Did not work
    - **Why:** It fixes Cargo only and keeps the same silent trap for any other ecosystem's lockfile. No file in a checkout other than `Cargo.lock` matched `*.lock` after a full `cargo test` run: the Monitor's runtime locks are created under `CODEX_HOME` or `TMPDIR`, and `benchmarks/` is ignored as a whole. The rule was removed instead.
  - **Attempt:** Keep the CI "Resolve Dependencies" step and add `--locked` to `cargo test`.
    - **Outcome:** Did not work
    - **Why:** `cargo generate-lockfile` rewrites the committed lockfile before the locked build, so `--locked` then checks the freshly resolved file against itself. The step was removed, and the policy rejects any cargo command without `--locked`, `generate-lockfile` and `update` included.
  - **Attempt:** Prove the lockfile is committed by checking that the file exists.
    - **Outcome:** Did not work
    - **Why:** An ignored lockfile exists in every developer tree that has built the crate. The rule asks git instead: the path must be a blob at `HEAD`, and `git ls-files --cached --others --ignored --exclude-per-directory=.gitignore` must not list it. `git check-ignore` was rejected because it also reads per-clone `.git/info/exclude` and the user's global excludes, which cannot keep the file out of another clone.
  - **Attempt:** Rely on the line-based scan of `run:` steps and scripts alone.
    - **Outcome:** Partial
    - **Why:** It cannot see indirect invocations (`$CARGO`, `eval`, cargo aliases). On GitHub Actions the policy also asserts that `Cargo.lock` still matches `HEAD` when the tests run, which any unlocked re-resolution that changed the graph would break.
- **Root cause:** A blanket ignore pattern written for generated files also matched a file that is a reviewed input, and CI then worked around the missing file instead of treating its absence as the defect.
- **Resolution:** `.gitignore` no longer ignores `*.lock`; `codex-switcher/Cargo.lock` is committed (direct dependencies: base64 0.22.1, brotli 9.0.0, chrono 0.4.45, clap 4.6.7, dirs 5.0.1, fs2 0.4.3, getrandom 0.2.17, libc 0.2.189, ring 0.17.14, serde 1.0.229, serde_json 1.0.151, ureq 2.12.1; 141 crates.io packages, all with checksums). CI runs `cargo test --locked --verbose` with the cache still keyed on `rust-toolchain.toml` and the committed lockfile; the installer runs `cargo build --release --locked`; the uninstall shell test builds with `--locked`. `codex-switcher/tests/ci_workflow_policy/` adds `locked_cargo.rs`, `lockfile.rs`, `cache_keys.rs`, and `git_repo.rs`.
- **Verification:** In `codex-switcher/` on rustc 1.98.1: `cargo fmt --check` clean; `cargo test --locked` passed on the branch; `cargo test --locked --test ci_workflow_policy` passed 99 tests; each integration test target passes `cargo clippy --locked --test <name> -- -D warnings`. On the branch alone, `cargo clippy --all-targets --locked -- -D warnings` reports only the two findings it already reported on `93b9c1a`, which `origin/main` fixed in #21; on a throwaway merge of the branch with `origin/main` (`f1a8e17`) the all-targets Clippy gate is clean and the full suite passes. Hand-applied mutations each made at least one test fail: ignoring flags after `--`; dropping the lookup, `fmt`, `name:`, redirection, continuation, tab-comment, quote-opening, or single-quote-literal handling; not reporting an unterminated quote; keeping quotes and backslashes inside words; skipping the `$(command -v cargo)` substitution; treating `CARGO` variables as never or always the command word; dropping either lockfile check; accepting a symlink as the committed lockfile; answering "not ignored" for a path git cannot see; keeping inherited `GIT_*` variables; accepting `hashFiles` patterns; matching any `ls-tree` entry; making the positive locked-build check ignore the subcommand, the flag, or `--`; and unwiring the rule. The CI-only lockfile check passed with `GITHUB_ACTIONS=true` and failed after appending a line to `Cargo.lock`. Missing evidence: no CI run on this branch yet; the first pull-request run should restore the exact key `macOS-cargo-49a04bed…-74f3856d…` saved by main, and must be confirmed on the PR head SHA.
- **Prevention/follow-up:** The policy tests above, including positive checks that `scripts/install.sh` runs a locked `cargo build` and a required-check job of `ci.yml` runs a locked `cargo test`; the AGENTS.md CI paragraph and the README "Dependency lockfile policy" section. The review of the scan itself is recorded in [2026-09-27-cargo-scan-comment-split-failed-open.md](2026-09-27-cargo-scan-comment-split-failed-open.md). Existing checkouts need no action: pulling replaces an ignored local `Cargo.lock` with the committed one. Confirm the first CI run and record it in a follow-up learning.
- **Reusable learning:** Commit the lockfile of anything that ships a binary, build it with `--locked` everywhere it is built (CI, installer, test scripts), and never regenerate it inside CI. Check a policy about committed files against git (`HEAD` and the versioned ignore rules), not against the working tree.
