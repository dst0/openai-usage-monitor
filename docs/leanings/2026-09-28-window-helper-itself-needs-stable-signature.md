# 2026-09-28 — The window helper itself needs a stable signature

- **Status:** Partial
- **Task/context:** Review of the launchd window-access fix in PR #47 before installation.
- **Unexpected observation or failure:** The proposed stable signing covered `cxi` but left `codex-window-restore` ad hoc signed, even though the helper calls both privacy preflights and performs the window reads.
- **Evidence:** `scripts/codex-window-restore.swift` calls `AXIsProcessTrusted()` and `CGPreflightScreenCaptureAccess()` in the helper process. [Apple's AX documentation](https://developer.apple.com/documentation/applicationservices/1460720-axisprocesstrusted?changes=l_9) explicitly defines the former as checking the current process. The installer previously compiled the helper directly to its installed path without a stable signature. [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) explains why an ad hoc designated requirement is version-specific. This extends [the earlier launchd finding](2026-09-28-launchd-window-access-needs-stable-identity.md): signing only `cxi` was insufficient to establish a stable identity for the process making the calls.
- **Approaches tried:**
  - **Attempt:** Keep stable signing on `cxi` alone. **Outcome:** Rejected. **Why:** The AX preflight runs in the helper, and actual TCC attribution for a spawned helper can differ from its parent.
  - **Attempt:** Route the work through the menu app. **Outcome:** Deferred. **Why:** A background restart must still work when the app is absent; this would require a new request channel and lifetime contract.
  - **Attempt:** Add `AssociatedBundleIdentifiers` to the legacy LaunchAgent. **Outcome:** Deferred. **Why:** [Apple's Service Management documentation](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos) requires the agent executable and associated app to have matching Team Identifiers. The installer signs `Codex Monitor.app` ad hoc, so a certificate-signed `cxi` would not meet that condition. The key's documented Login Items association does not prove Accessibility or Screen Recording access.
  - **Attempt:** Sign both existing executables with fixed identifiers. **Outcome:** Implemented in source. **Why:** It preserves the Rust daemon architecture and gives either attributed client a cross-build identity when the same certificate is selected.
- **Root cause:** The implementation treated the launchd parent as the only relevant TCC client while performing the guarded operation in a separate ad hoc signed process. Which executable macOS records as responsible on this host remains unverified without an authorized launchd run.
- **Resolution:** Compile the helper to a same-directory staging path, sign it with the same selected identity as `cxi` and fixed identifier `com.codex.monitor.window-restore`, verify its signature, then atomically replace the installed helper. Extend cleanup and uninstaller coverage for its interrupted staging files. Without an identity, both remain ad hoc signed.
- **Verification:** `tests/install_cli_staging_signature.sh`, `tests/install_lock.sh`, and `tests/log_permissions_and_uninstall.sh` passed on macOS 27.2. No installed binary, live TCC entry, Desktop window, or grant was changed or tested. A valid certificate is unavailable on this host, so grant retention remains unverified.
- **Prevention/follow-up:** Grant each denied service only to the client macOS attributes the launchd helper request to, then verify both from that context and run the selected-task restore rehearsal before enabling automatic switching. Do not add `AssociatedBundleIdentifiers` until the app and agent share a valid signing team and its TCC effect is verified. Keep the preflight fail closed.
- **Reusable learning:** Give the executable that calls a privacy API its own stable signing identity; do not infer a helper's authorization solely from its parent.
