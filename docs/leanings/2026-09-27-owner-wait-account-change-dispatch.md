# 2026-09-27 — Owner wait crossed an account change before recovery dispatch

- **Status:** Resolved
- **Task/context:** Guard owner-routed task recovery while the official ChatGPT Desktop resolves or mounts a task after account distribution or explicit `cxi resume`.
- **Unexpected observation or failure:** A manual switch of the shared auth file during the Desktop owner wait could allow a recovery request under a different account and consume the saved checkpoint.
- **Evidence:** A fake Desktop IPC router changed synthetic auth from account A to B after reading `thread-owner-discovery` and before replying. Before the fix, `ExplicitTarget` sent `thread-follower-start-turn`, marked the task dispatched, and removed the checkpoint. The wait can last up to 90 seconds in the live path.
- **Approaches tried:**
  - **Attempt:** Rely on the account check before calling recovery and on the deferred target binding in the dispatch marker.
    - **Outcome:** Did not work
    - **Why:** The check preceded the owner wait, while the marker compared accounts only for unattended deferred targets.
  - **Attempt:** Check only the visible recovery banner after owner discovery.
    - **Outcome:** Rejected
    - **Why:** Banner liveness proves a window and process, not the active shared auth account.
  - **Attempt:** Pin the verified active account and exact Desktop PID and birth identity at recovery start, then compare fresh values immediately before every irreversible dispatch marker.
    - **Outcome:** Partial
    - **Why:** It caught a change during owner discovery, but a second red test changed auth during marker write and still sent IPC. A hidden banner captured before restart also named the old process and was rejected at recovery start.
  - **Attempt:** Bind a hidden captured-restart banner through the relaunched process's exact live Desktop session marker, then recheck identity after the durable marker and restore the original checkpoint with readback before any IPC on mismatch.
    - **Outcome:** Worked in focused synthetic tests
    - **Why:** A captured restart can pin its validated new PID and birth identity, while other modes keep their original process boundary. Changes during owner wait or marker write stop both queued and turn-start dispatch with no checkpoint loss.
- **Root cause:** `mark_dispatch_attempt` reread the current binding but compared it to the saved account only for deferred unattended retries. Explicit, captured, and discovery recovery had no pinned account for a later comparison.
- **Resolution:** `RecoveryDispatchIdentityGuard` records the uniquely matched active auth account and exact Desktop process at operation start. A hidden captured restart uses a managed Desktop session marker whose PID and birth identity match the live process, checked twice; other modes keep the banner's original identity. `RecoveryDispatchCheckpointService` checks identity before and after durable marker write. A mismatch before IPC restores the exact original checkpoint and verifies readback. A marker write error after rename also triggers the same restoration. An explicit claim still bypasses an *older* deferred binding, but never a change to the account that began the explicit operation; finalization keeps its old offset and owner account. A previously unbound target keeps its offset and becomes bound to the starting account, preventing retry under the changed account.
- **Verification:** The no-queue fake-router test failed before the guard with an owner-routed turn-start IPC. Queued and no-queue tests then failed when auth changed during marker write. All four pass after the two checks and exact `PendingTarget` restoration. A hidden captured-restart test failed with the old banner PID, then passed with exact managed-session rebinding; non-restart mode, missing marker, and marker P1/live P2 reject the change. A synthetic post-rename marker write failure restores and reads back the exact checkpoint. A composition test writes, finalizes, prunes, and reloads an explicit claim, retaining its original offset and owner account. `cargo test --workspace --locked --quiet -- --test-threads=1` passed 541 unit tests and all integration suites (2, 2, and 7); `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo fmt --check`, and `git diff --check` passed. A live cross-account cold-task run remains unverified.
- **Prevention/follow-up:** Keep checks adjacent to checkpoint consumption and IPC; any wait, disk write, or UI step after an earlier check can admit a manual account change. Desktop's own menu is outside Monitor's operation lock, so a change in the remaining interval between the final check and IPC cannot be made atomic by this project alone. Continue to leave automatic switching off until cold-task mounting and exact multiwindow restoration are proved in the installed app.
- **Reusable learning:** Snapshot the verified account and process at recovery start, revalidate before and after durable marker write, and restore the exact checkpoint if identity changes before IPC.
