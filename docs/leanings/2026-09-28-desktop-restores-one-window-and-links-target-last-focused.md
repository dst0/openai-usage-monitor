# 2026-09-28 — Desktop restores one window, and task links target the last focused window

- **Status:** Partial
- **Task/context:** Preserving each ChatGPT window's selected Codex task across a Monitor-driven Desktop restart (`cxi restart`, `cxi switch`). This follows [the active-probe learning](2026-09-27-multiwindow-task-mapping-needs-active-probe.md) and [the synthesized-shortcut learning](2026-09-27-synthesized-desktop-shortcut-needs-keymap-and-focus-proof.md), whose probe pinned ChatGPT 26.924.20706 and therefore refuses the installed 26.924.22138.
- **Unexpected observation or failure:** The installed Desktop has no multiwindow restoration of its own, and a task deep link does not name a window: it navigates whichever primary window was focused last. Separately, the probe from PR #25 could never run on the owner's machine: the owner's `~/.codex/keybindings.json` holds one unrelated override (a dictation hotkey), and the probe accepted only an absent, blank, or `[]` keymap.
- **Evidence:** Read-only inspection of a copy of `/Applications/ChatGPT.app/Contents/Resources/app.asar` for `com.openai.codex` 26.924.22138 (build 11645); no Desktop process was launched or touched.
  - Window persistence: the window manager stores one `electron-main-window-bounds` record in the Desktop global state, written when a primary window closes and, for the most recently active primary window, when the app starts quitting; every new primary window starts from that record. No list of windows, per-window route, or per-window task is persisted. The `update-resume-state-v1` record holds only thread IDs to resume after an in-app update, with a 15-minute expiry. `thread-tab-routes-v1:<thread>` and `thread-client-id-v1:` records are keyed by thread, not window.
  - Launch: one primary window is created with no initial route; the renderer's router is an in-memory router seeded only from an `initialRoute` query parameter, so the window does not reopen a previous task by itself.
  - Deep links: `codex://threads/<id>` resolves the target with `ensureWindow({forNavigation: true})`, which takes `getPrimaryWindow()`, the most recently active primary window (tracked from each window's `focus` event), shows and focuses it, reads the thread, and sends `navigate-to-route` to that window only. There is no parameter that selects or creates a window.
  - New windows: File > New Window exists only when the `multiWindow` feature gate is on (the main process defaults it to off and inserts the item once the renderer reports the feature, so it can be missing right after launch); it calls `createFreshWindow('/')`, which creates, shows, and focuses a primary window at the persisted bounds. The renderer's `open-in-new-window` message and the "Open in New Window" command are renderer-internal and not reachable from outside the app. The Dock menu offers recent threads, not a new window.
  - Closing: on macOS, closing the last primary window hides it; closing any other primary window destroys it.
  - Desktop IPC: the router's methods are `thread-stream-*`, `thread-read-state-changed`, `thread-archived`, `thread-unarchived`, `thread-owner-discovery`, `thread-follower-*`, `thread-queued-followups-changed`, and `ipc-connection-reset`. Owner discovery is answered by one IPC client per host in the main process (`getStreamRole(thread).role === "owner"`), so its client ID identifies the Desktop host connection, never a window. No window, route, or navigation method exists.
  - Copy deeplink: unchanged from 26.924.20706. The hidden `copyDeeplink` menu item (`visible: false`, `acceleratorWorksWhenHidden: true`) defaults to `CmdOrCtrl+Alt+L`, the only default binding on that chord; its click handler sends `copy-deeplink` to `BrowserWindow.getFocusedWindow()`, falling back to the primary window. The renderer writes exactly `codex://threads/<id>` through `navigator.clipboard.writeText`, and only when a thread is selected.
  - Keymap: `join(CODEX_HOME ?? ~/.codex, "keybindings.json")` is parsed as an array of `{command: string, key: string | null}`; any parse or schema failure means defaults. Five legacy command names are aliased (`closeTabOrWindow`, `focusQuickChat`, `newThread`, `toggleBrowserPanel`, `toggleSidePanelFullWidth`), none to `copyDeeplink`. A command with file entries uses exactly those keys (a `null` key removes its binding); other commands keep their defaults. Chords are normalized by lower-casing, mapping `cmdorctrl`/`cmd`/`command`/`super` to `meta` and `option` to `alt`, and sorting. Therefore `copyDeeplink` keeps Cmd+Opt+L exactly when no entry names it, and no other command gains that chord unless an entry binds it.
  - Live environment (read-only, 2026-09-28): the U.S. layout is selected, no `NSUserKeyEquivalents` exist for `com.openai.codex` or globally, and the pasteboard access behavior for this terminal's processes is "always allow" (2).
- **Approaches tried:**
  - **Attempt:** Rely on Desktop's own window restoration after a graceful quit and relaunch.
    - **Outcome:** Did not work (by inspection).
    - **Why:** Only one window's bounds are persisted, and the relaunched window starts on the home route.
  - **Attempt:** Tie IPC owner discovery to a window.
    - **Outcome:** Did not work (by inspection).
    - **Why:** Ownership is per host connection in the main process, not per renderer window.
  - **Attempt:** Drive navigation through the renderer's `open-in-new-window` message or the "Open in New Window" command.
    - **Outcome:** Did not work (by inspection).
    - **Why:** Both are renderer-internal; no external route reaches them.
  - **Attempt:** Snapshot each window's task with Copy deeplink, then after relaunch create each extra window with File > New Window, focus the target window, open its task link, and verify with Copy deeplink.
    - **Outcome:** Partial.
    - **Why:** Every step is supported by the inspected code and by hermetic tests of the sequencing (a scripted Desktop that routes links to its last focused window), but none was exercised on the live Desktop: ChatGPT was not running during this work, and launching it would have started the owner's active heartbeat automations ([details](2026-09-28-launching-desktop-starts-owner-heartbeat-automations.md)). Unobserved live: whether AX focus requests key the target window in an inactive app, whether File > New Window is present and pressable through Accessibility, whether a new window's `focus` event always precedes the link, how long a cold task takes to mount after a relaunch, and how many pasteboard writes Chromium makes per copy.
- **Root cause:** Desktop treats windows as disposable views over shared state; it persists one window frame and routes deep links through its most recently focused primary window.
- **Resolution:** `cxi restart --restore-window-tasks` and `cxi switch <account> --restore-window-tasks` capture every window's task, frame, and focus before shutdown (failing closed, so the multiwindow guard still refuses the restart), and after the relaunch place the first window, open the rest with New Window, send each link only while the target window has keyboard focus, and count a window only when its own Copy deeplink returns the planned task; the restore runs again after recovery when recovery had targets. The shutdown guard accepts more than one window only for exactly the captured window IDs. `cxi window rehearse-task-restore --allow-focus-and-clipboard` exercises the same steps in temporary windows without a restart. Nothing automatic passes the flag, and auto-switch stays disabled.
- **Verification:** Code inspection, hermetic Swift sequencing tests (`tests/CodexWindowTaskSessionCoreTests.swift` against a scripted Desktop in `tests/CodexWindowTaskFakeDesktop.swift`), shared JSON fixtures read by both Swift and Rust tests (`tests/fixtures/window-tasks/`), and Rust service, validation, guard, CLI, argument, and isolation tests. Mutating any of these makes a test fail: the focus check before each link, the post-navigation focus recheck, the check of earlier windows before a second link, the final recheck pass, the keyboard-focus and exactly-one-window checks for New Window, the wait for the New Window item, the process-birth checks before a press, a frame change, a close, or a refocus, the snapshot's full-screen and New Window checks, the plan duplicate check, the layout check, the recheck's recovery-task filter, the originals check, the refocus after a successful or failed snapshot, restore, or recheck, the clipboard ownership record, the rehearsal's frame reset and window cleanup, and inverting the forwarded flag in either restart command. No window, clipboard, deep link, or Desktop process was touched live.
- **Prevention/follow-up:** The owner should run `cxi window rehearse-task-restore --allow-focus-and-clipboard` with two and then three windows, then `cxi restart --restore-window-tasks` with no running turn and no heartbeat due, and record the results in a new linked learning before auto-switch is considered. The rehearsal uses tasks that are already loaded in a running Desktop, so it cannot show how a cold task loads after a relaunch, when New Window appears after a relaunch, or how the relaunched window is reused; only the restart shows those. Re-inspect the bundle after each ChatGPT update.
- **Reusable learning:** A deep link to an Electron app with several windows goes wherever the app's own "last focused" bookkeeping points; prove that focus before sending the link and verify the result afterwards.
