# 2026-09-28 — Distribution window task capture was disconnected

- **Status:** Partial
- **Task/context:** Restore the selected task in each Desktop window after automatic and Menu Bar account distribution restarts.
- **Unexpected observation or failure:** The existing direct CLI `--restore-window-tasks` path had a task snapshot and restore helper, but running-Desktop distribution used only window geometry. It could stop a Desktop with selected tasks and relaunch into the wrong or empty task. A mock distribution test initially passed while production `SystemAppLifecycle` task hooks were absent.
- **Evidence:** A regression with a synthetic `WINDOW_ACCESS_FAILED` task capture initially reached distribution success. Source inspection showed no production distribution task capture, while the direct CLI path had `WindowTaskRestartSession`. The fake helper and distribution regressions now exercise the production capture seam and pre-stop rollback.
- **Approaches tried:**
  - **Reuse the explicit CLI flag through distribution:** Rejected. Its user trigger gate and direct-switch ownership would blur the distinction between user-requested direct restarts and internal distribution.
  - **Put task switching in Swift:** Rejected. It would duplicate account orchestration and lose the Rust journal and rollback sequence.
  - **Own a task session in the Rust distribution lifecycle:** Worked in synthetic tests. The same `WindowTaskRestartSession` and helper are used while distribution retains ownership of checkpoint, auth, recovery, and banner state.
- **Root cause:** Distribution and direct CLI restart had separate lifecycle coordinators. Window geometry preservation did not preserve the selected task, and multiwindow refusal did not solve the single-window case.
- **Resolution:** Capture tasks after the banner obtains an exact process identity; carry exact window IDs through both preflights and stop; require a pre-stop Desktop IPC handshake for a selected-window task even without recovery targets; compare the complete selected-task snapshot before SIGTERM; restore after verified relaunch and recheck after recovery; report a lost window as partial success. A verified zero-window inventory remains an exact empty set.
- **Verification:** Synthetic tests cover zero, one, and two windows; access failure; a new window after zero capture; task change under the same PID and window ID; IPC preflight refusal with one selected window and no recovery targets; zero-window IPC fast path; IPC readiness or target binding failure before a task link; production lifecycle capture with a fake helper; and failure to signal when final task/window verification fails. On the final code, `cargo check --locked`, `cargo test --locked -q` (801 unit tests plus integration suites), and `cargo clippy --workspace --all-targets --locked -- -D warnings` passed. No installed-app multiwindow rehearsal or live automatic switch has run.
- **Prevention/follow-up:** Keep automatic switching disabled until installed-app selected-task restoration and cold-task mounting are verified. A narrow interval remains between final task read and SIGTERM, and between post-IPC identity checks and a task link. Ownerless-only deferred recovery may have no visible banner when geometry preservation is disabled; track that UI gap separately.
- **Reusable learning:** Any path that restarts a running Desktop must own an exact selected-task snapshot, refuse an unverified pre-stop state, and report post-relaunch loss without claiming complete success.
