# 2026-09-27 — An in-process flock models a Desktop writer lock in detection tests

- **Status:** Resolved
- **Task/context:** Replacing the removed live smoke test for `detect_in_progress_threads()` (`codex-switcher/src/switcher/thread_detection_service.rs`) with hermetic tests. [2026-09-26-tests-fell-back-to-live-codex-home-and-network.md](2026-09-26-tests-fell-back-to-live-codex-home-and-network.md) records why `test_detect_in_progress_live` was removed. This entry keeps only the facts that entry does not cover. They came from an abandoned parallel session and were merged into this branch's detection tests.
- **Unexpected observation or failure:** The detector cannot observe a writer lock without trying to take it. It opens each `thread-writer-locks/*.lock` read-write and calls `try_lock_exclusive()`. On a lock that no app-server holds, the call succeeds, so the detector itself briefly holds an exclusive flock. Against the live `~/.codex`, a test therefore held locks that a starting ChatGPT app-server worker could need. It also ran `/usr/bin/sqlite3` against the live `state_5.sqlite`, and its result depended on the owner's current tasks.
- **Evidence:** A detection test holds its own locks through separate open file descriptions, and the detector opens its own descriptor for the same file. `flock(2)` locks belong to an open file description, so the detector sees those locks as held even inside the same process. After detection, a fresh descriptor can take the unheld lock and cannot take the held ones. A leaked probe descriptor or a disturbed writer lock would show up in that check.
- **Approaches tried:**
  - **Attempt:** Keep the live smoke test and mark it `#[ignore]`.
    - **Outcome:** Rejected.
    - **Why:** An explicit run would still take live writer locks, and the test asserted nothing.
  - **Attempt:** Seed a private `CODEX_HOME` with a `threads` table, rollout files, and lock files. The test holds most locks itself with `fs2::FileExt::lock_exclusive`, leaves one lock file unheld, and omits lock files to model a writer that already released them after a quota error.
    - **Outcome:** Worked.
    - **Why:** No second process is needed to model a running writer. `TestCodexHome` stays alive until the lock checks finish, so every probe and every check sees the test's home.
- **Root cause:** A diagnostic live test stayed in the unit suite, and a flock probe has a write-side effect.
- **Resolution:** `thread_detection_service.test.rs` keeps #19's two quota-timestamp tests and adds three detection tests. `detects_only_live_or_recent_quota_user_threads_in_an_isolated_home` expects four threads: active with a held lock, recent quota with a held lock (reported once across both phases), recent quota with a released lock, and a held quota thread without `updated_at` that only its rollout failure time dates. It excludes active without a writer, stale quota in either phase, a held quota thread whose `updated_at` a reopen refreshed but whose failure is five hours old, clean completion, a non-quota error, `turn_aborted` without a journal, a subagent, and an archived thread. It also asserts that the unheld lock is left unheld and the held locks stay held. `restart_journal_adds_captured_targets_and_withholds_ownerless_ones` adds a captured `turn_aborted` target, does not repeat a captured target that detection already found, and withholds ownerless retries from both phases. `unreadable_recovery_journal_blocks_all_detection` shows that the same home reports threads without a journal and nothing with an unparseable one. Quota fixtures carry a `timestamp` on `task_complete`, because since #19 detection dates a quota failure from that event rather than from SQLite.
- **Verification:** 15 temporary detector mutations were applied to the source one at a time and reverted after each run, on main at 93b9c1a. 14 made a test in `switcher::` fail: treating every lock as held, dropping the phase-1 user filter, dating a phase-1 quota failure from `updated_at`, dropping phase-1 quota recency, dropping the phase-2 dedup, leaking the probe descriptor, counting `turn_aborted` in phase 1, dropping the journal merge, dropping the ownerless filter, ignoring an unreadable journal, dropping the journal dedup, dropping journal quota recency, dropping journal active/aborted recency, and dropping the phase-2 window. Dropping the phase-2 `is_user_thread` filter survived because the phase-2 SQL already excludes archived and subagent rows.
- **Prevention/follow-up:** AGENTS.md already says that probing a writer lock with `try_lock_exclusive` briefly takes it. Outside this learning's fix and not investigated: the production detector still briefly takes a free writer lock when it probes, and no evidence yet shows whether that can race a starting app-server. The tests model a writer with the same `fs2` (`flock(2)`) primitive the detector probes with; that Desktop's app-server uses `flock(2)` rather than `fcntl` record locks is an assumption of the production detector, not something these tests verify.
- **Reusable learning:** A flock probe is a write. Run lock-probing code in tests only against a private `CODEX_HOME`, hold the test's own locks through a separate descriptor to model a running writer, and check lock state again after the code under test runs.
