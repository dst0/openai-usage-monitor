# 2026-09-28 — Swift's "SDK is not supported" error came from an unwritable module cache

- **Status:** Resolved
- **Task/context:** Cell E of the module-cache comparison in [2026-09-28 — Swift module cache fails only when reused through another path spelling](2026-09-28-swift-cache-spelling-mismatch-isolated.md). The goal was to confirm that this host still cannot build with its default SDK, as recorded in [2026-09-25 — Swift compiler and default SDK version mismatch](2026-09-25-swift-toolchain-sdk-version-mismatch.md) and [2026-09-25 — Swift SDK/compiler mismatch blocked the local release gate](2026-09-25-swift-sdk-compiler-mismatch-blocked-local-release-gate.md). `CODEX.md` required `SDKROOT=.../MacOSX26.5.sdk` for that reason.
- **Unexpected observation or failure:** With a writable module cache, the default macOS 27.0 SDK builds everything, even though its Swift interfaces (`6.4.0.31.4`) differ from the compiler (`6.4.0.34.1`). The recorded failure appears only when the module cache cannot be written, and it appears with the 26.5 SDK too.
- **Evidence:**
  - The Command Line Tools packages and SDKs have not changed since 2026-09-14, before both 2026-09-25 records. All `com.apple.pkg.CLTools_*` packages are `27.0.0.0.*` with that install time.
  - Default SDK, no `SDKROOT`, a new writable `CLANG_MODULE_CACHE_PATH`: the four `scripts/install.sh` compiles passed 3 of 3 runs. The driver used `-sdk /Library/Developer/CommandLineTools/SDKs/MacOSX.sdk`, which links to `MacOSX27.0.sdk`. The fixed `./scripts/test_swift.sh` also passed every suite with the default SDK (runs listed in the PR).
  - Read-only module cache (`chmod 555`), compiling `import Darwin`: 3 of 3 runs with the default SDK and 3 of 3 with `SDKROOT=.../MacOSX26.5.sdk` failed. Each printed `unable to open output file '.../SwiftShims-….pcm': 'Permission denied'` first, then `failed to build module 'Swift'; this SDK is not supported by the compiler (the SDK is built with '…'...`. Only the quoted SDK version changed between the two SDKs.
  - Local agent transcripts for 2026-09 hold 7 command results with `this SDK is not supported by the compiler`. All 7 also show `unable to open output file '~/.cache/clang/ModuleCache/…': 'Operation not permitted'`, because the agent sandbox denied the default cache. One of the 7 used the 26.5 SDK. No recorded run had a writable cache and still hit that error.
- **Approaches tried:**
  - **Attempt:** Build with the default SDK and a writable cache (the combination the 2026-09-25 records never tried).
    - **Outcome:** Worked.
    - **Why:** The compiler rebuilds the SDK's Swift modules from their interfaces into the writable cache.
  - **Attempt:** Build with an unwritable cache under each SDK.
    - **Outcome:** Did not work, with either SDK.
    - **Why:** The interface rebuild cannot write its output. Swift then reports the SDK/compiler version difference as the reason the rebuild failed.
- **Root cause:** When rebuilding an SDK module from its interface fails, Swift reports it as `this SDK is not supported by the compiler` if the SDK was built by a different compiler version. Both SDKs here were, and the message followed a cache write failure with each. The failures on 2026-09-25 were caused by the sandbox blocking the default module cache. The earlier fix changed two things at once: a writable cache and the 26.5 SDK. Only the writable cache was needed.
- **Resolution:** `CODEX.md` and `README.md` now say the version difference alone does not block builds on this host. They tell readers to check the error printed before the "not supported" line, and to use a writable `CLANG_MODULE_CACHE_PATH` when the default cache is denied. `SDKROOT=.../MacOSX26.5.sdk` still works but is no longer required. The two 2026-09-25 records are marked `Corrected` where they called the version difference decisive.
- **Verification:** The runs above. The default module cache location (`~/.cache/clang/ModuleCache`) was not exercised, to avoid writing to user-owned state outside scratch directories. Whether an ordinary unsandboxed shell can use it on this host is therefore unverified.
- **Prevention/follow-up:** `scripts/swift_module_cache.sh` rejects an unwritable `CLANG_MODULE_CACHE_PATH` before `install.sh` or `test_swift.sh` compiles, naming the real cause (`tests/swift_module_cache_path.sh`). The default cache is not checked. When a Swift build reports an unsupported SDK, read the preceding errors before changing SDKs. If they mention the module cache, fix cache writability first. Remove the SDK override from any local runbook that still requires it.
- **Reusable learning:** "This SDK is not supported by the compiler" is a wrapper around a failed interface rebuild, not a diagnosis. Find the first error in the output, and test one variable at a time before recording a toolchain mismatch as the cause.
