# 2026-09-28 — Concurrent Swift suite runs isolated by an injected defaults store

- **Status:** Resolved
- **Task/context:** Follow-up to the `Open` record [2026-09-28 — Concurrent Swift suite runs share the AppDelegate test's defaults](2026-09-28-concurrent-swift-suites-share-test-defaults.md), which saw one of two parallel `./scripts/test_swift.sh` runs fail at `tests/AppDelegateTests.swift:253` and left the cause as a hypothesis. This work reproduced the failure on demand, then gave every Swift test its own defaults store.
- **Unexpected observation or failure:** Besides the reported line 253 (`Default stackPercentages must be true`), concurrent runs also failed at line 257 (`stackPercentages must reflect updated value false`). The old Test 4 only exercised `UserDefaults` itself, while the production readers it was meant to cover (`AppDelegate` menu, status bar, and toggle) also used the shared store, as did every `AppDelegate()` other tests built. The shared `app_delegate_test` domain on this host also held a launch-at-login key that no code in this repository writes, apparently from another project's test binary with the same name.
- **Evidence:** All reproductions ran the AppDelegate test binary under an executable name private to the reproduction, so its standard domain was private too and no other run on the host was disturbed. For a bundle-less binary the standard domain is the executable's name (checked by copying a probe binary under a new name).
  - Deterministic interleaving: under `lldb`, the pre-fix binary stopped after line 251's `removeObject`, another process ran `defaults write <domain> stackPercentages -bool false`, and the run resumed. It failed at line 253 with the reported message 3 of 3 times. The same stop without the write passed line 253 2 of 2 times (`defaultPref = true`).
  - Two copies of the pre-fix binary started together, sharing one domain: 26 of 30 pairs failed, at line 253 or line 257.
  - A second process writing `false` into the binary's domain in a loop: the pre-fix binary failed at line 253 in 2 of 10 runs.
  - Red step: with the store injected into `AppDelegate` but its readers still on the standard store, the new Test 4 failed at `tests/AppDelegatePreferencesTests.swift:73` with `[true] != [false] - stackPercentages must be read from the given store`.
  - After the fix: 0 of 30 concurrent pairs and 0 of 10 writer runs failed. Under `lldb`, writing `stackPercentages`, `codex_refresh_interval`, and `CodexMonitorLaunchAtLogin` into the binary's standard domain before Test 4's first read left every Test 4 assertion passing, 3 of 3 times. Run alone under a private name, the fixed binary created no preferences domain at all; the pre-fix binary left `stackPercentages = 1` in its own.
  - Two full `./scripts/test_swift.sh` runs at the same time from one checkout, each with its own module cache, after the fix: 6 of 6 pairs (12 runs) passed, each running the new Test 4.
- **Approaches tried:**
  - **Attempt:** Run the suite one at a time per user account (the `Open` record's interim advice).
    - **Outcome:** Partial.
    - **Why:** It avoids the race, but several agents run worktrees of this repository on one host, and a run from any checkout, or from another project with a binary of the same name, still shares the domain.
  - **Attempt:** Give the test binary a unique name per run, so its standard domain is unique.
    - **Outcome:** Rejected.
    - **Why:** It leaves a plist in `~/Library/Preferences` per run, and tests still cannot set a preference for the production code without writing the process-wide store.
  - **Attempt:** A protocol wrapper around preferences with an in-memory test store.
    - **Outcome:** Rejected.
    - **Why:** It adds a layer to the Swift app for tests only, and tests would stop exercising real `UserDefaults` behavior such as reading an unset key as the stacked default.
  - **Attempt:** A named `UserDefaults(suiteName:)` per run, removed with `removePersistentDomain(forName:)`.
    - **Outcome:** Did not work.
    - **Why:** The removed domain's plist stays in `~/Library/Preferences`; see [2026-09-28 — `removePersistentDomain(forName:)` leaves an empty plist in ~/Library/Preferences](2026-09-28-remove-persistent-domain-leaves-empty-plist.md).
  - **Attempt:** Inject the store into `AppDelegate`, and give tests a suite named by an absolute path in a private directory.
    - **Outcome:** Worked.
    - **Why:** Each run's store is a file no other process knows about, and the production code under test reads and writes exactly that store.
- **Root cause:** Confirmed. `AppDelegate` and the old Test 4 used the standard defaults store, which for the bundle-less test binary is the per-user `app_delegate_test` domain that every concurrent run shares. Another run's write between this run's write and read changed what this run read.
- **Resolution:** `AppDelegate` takes its store and login-item manager through `init(client:defaults:autoLaunchManager:)`. `AppDelegate()` passes `UserDefaults.standard` and `AutoLaunchManager.shared`, so the app still reads the user's saved preferences under the same keys. `tests/TestPreferencesSuite.swift` provides a per-run suite and refuses to run as the Monitor's bundle identifier (read from `resources/Info.plist`). The new Test 4 (`tests/AppDelegatePreferencesTests.swift`) requires both stored values of each preference to reach the delegate, the menu, and both status-bar paths, and the menu actions to write only the given store. Login items are stubbed, so the suite no longer asks System Events through `osascript`. `tests/swift_test_defaults_isolation.sh` rejects a Swift test or source that uses the standard store outside the two production composition roots; `scripts/test_swift.sh` and a required CI step run it.
- **Verification:** `./scripts/test_swift.sh` passes; `cargo test --locked --test ci_workflow_policy` passes; the reproductions above.
- **Prevention/follow-up:** The static check and the Test 4 value checks guard the fix. Remaining shared state in the Swift tests that is not preferences: the AppDelegate suite builds menus with `CodexClient.shared`, which reads the live `~/.codex` unless `CODEX_HOME` is set. The new Test 4 points `CODEX_HOME` at a path that does not exist; the older tests do not. A suite's search list still includes the user's global domain (`NSGlobalDomain`), so a Monitor key written there would reach both the app and these tests; nothing in this repository writes one.
- **Reusable learning:** A Swift test binary without a bundle shares its standard defaults with every other run of a binary of that name. Inject the store into the code under test and give each run a suite in its own temporary directory.
- **References:** `Sources/AppDelegate.swift`, `tests/TestPreferencesSuite.swift`, `tests/AppDelegatePreferencesTests.swift`, `tests/swift_test_defaults_isolation.sh`, `scripts/test_swift.sh`.
