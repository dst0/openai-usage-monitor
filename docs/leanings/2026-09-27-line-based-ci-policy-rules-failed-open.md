# 2026-09-27 — Line-based CI policy rules failed open

- **Status:** Resolved
- **Task/context:** Fix two review findings on PR #13 against `codex-switcher/tests/ci_workflow_policy/`, the test crate that enforces the CI baseline on `.github/workflows/` with a hand-written line reader instead of a YAML dependency, then address an adversarial test-critic review of the fixes.
- **Unexpected observation or failure:** Both rules passed workflows they exist to reject. The checkout rule accepted `persist-credentials: false` anywhere below the step, for example under `env:`, although `actions/checkout` persists the token unless its own input says otherwise. The required-check rule only rejected path filters found under `on:`; `on: push` and `on: [push]` leave that block empty, so the suite stayed green for a workflow that never runs on pull requests. The critic then found more of the same class: a required job could still report success without doing its work (`needs:` on a job skipped for PRs, step-level `continue-on-error: true`, a step `if:` that skips the test step, a second job with the same name), and YAML that libyaml reads differently from the line reader passed every rule (anchors, aliases, and tags on keys or values, double-quoted escapes such as `"u\x73es"`, lone CR, NEL, U+2028, and U+2029 line breaks, `<<` merges, `?` keys, and quoted or flow values continued on the next line). It also found false positives on valid compact sequences (`schedule:` followed by `- cron:` at the same indentation) and on `pull_request: {}`.
- **Evidence:** Each regression test failed before its fix, reporting no violation for the bypass: `persist_credentials_must_be_a_direct_with_input` (`env:` case), `continued_or_merged_nodes_cannot_fake_checkout_inputs`, `a_pull_request_trigger_is_required` (`on: push`), `checkout_outside_a_step_or_in_another_spelling_is_still_checked` (`actions/checkout/@<sha>`), `required_jobs_need_only_other_required_jobs`, `required_job_steps_cannot_skip_or_mask_their_work`, `each_required_context_names_exactly_one_job`, and `node_properties_escapes_and_foreign_line_breaks_are_unreadable`. PyYAML 6.0.3 (libyaml) and Ruby Psych 3.1.0 (libyaml 0.2.1) both parse an `env:` value `"inputs follow` plus the next `with:` lines as one string, expand `- <<: *checkout` with its own `with: {fetch-depth: 0}` into a checkout without `persist-credentials`, read `? if` / `: ${{ false }}` as a job `if:`, and read a bare `on:` key as boolean `true`. Across 814 workflow files found locally, the whole-workflow check flags 126 lines in 59 files, all multi-line flow sequences; the anchor, tag, escape, and line-break rejections added none.
- **Approaches tried:**
  - **Attempt:** Keep the descendant search and exclude known wrong parents such as `env:`.
    - **Outcome:** Did not work
    - **Why:** The wrong parents are open-ended: block scalars of other inputs, nested mappings, and sibling blocks all contain the same text.
  - **Attempt:** Require exactly one direct `persist-credentials: false` member of the owning step's single `with:` block mapping.
    - **Outcome:** Partial
    - **Why:** Correct for plain block YAML, but a multi-line quoted scalar, an anchor, or a foreign line break can make lines the reader sees as keys mean something else.
  - **Attempt:** Add a YAML parser dev-dependency and parse properly.
    - **Outcome:** Did not work
    - **Why:** It adds a supply-chain input to a pinning PR whose `Cargo.lock` is gitignored, rewrites the whole suite for review fixes, and the parsers at hand do not read workflows as GitHub does either (`on` becomes `true`).
  - **Attempt:** Make the line reader smarter about anchors, escapes, and multi-line values.
    - **Outcome:** Did not work
    - **Why:** Each new shape adds parsing code that can itself be wrong. This linter guards the owner's own `ci.yml`, not hostile input, so rejecting the shapes it cannot read costs little.
  - **Attempt:** Keep the line reader, make each rule require its positive condition, and reject workflow-wide every shape the reader cannot represent.
    - **Outcome:** Worked
    - **Why:** The rules accept only shapes whose meaning the reader can see, and an empty or unreadable block is a violation instead of a pass.
- **Root cause:** The rules were written as "no forbidden text found" checks over loosely bounded text. They searched descendants instead of the exact structural parent, treated an empty or unparsed block as compliance, checked only a job's own keys rather than everything that can skip it, and assumed every line the reader saw was a key.
- **Resolution:** `checkout.rs` locates the step from its `- ` marker and key column and requires one `with:` block mapping with exactly one direct `persist-credentials: false`. A step counts as a checkout when its `uses:` owner and repository segments are `actions/checkout` in any case and with any path or ref. `triggers.rs` requires exactly one unconditional `pull_request` trigger for the branch named in `scripts/setup-github-protection.sh`. `required_checks.rs` requires each context to name exactly one job; that job may only need other required jobs, and its steps may not set `continue-on-error` or use an `if:` other than `always()` or `success()`. `yaml_limits.rs` rejects unreadable shapes in every workflow. `yaml_lines.rs` reads compact sequences as their key's value.
- **Verification:** `cargo test --test ci_workflow_policy` passes on rustc 1.98.1 with the live `.github/workflows/ci.yml` still compliant. Hand-applied mutations of each new condition each made at least one test fail. Renaming `ci.yml` locally made `every_workflow_meets_ci_baseline` fail.
- **Prevention/follow-up:** AGENTS.md states each requirement and the readable-YAML constraint. Known limits: multi-line flow sequences, common in other projects, are rejected rather than read; a multi-line plain `name:` is read as its first line only; a checkout mentioned inside a `run: |` script is reported; GitHub's own workflow parser was not exercised, so the rejections rely on libyaml behavior; branch globs such as `'**'` are rejected rather than evaluated.
- **Reusable learning:** A policy check must bind each required setting to its exact structural parent, require the positive condition rather than only the absence of forbidden keys (an empty or unparsed block is a violation), cover everything that can skip the checked work (conditions, dependencies, duplicates), and reject input shapes its reader cannot represent instead of guessing.
